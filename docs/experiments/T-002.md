# T-002 — Routed-item responsiveness baseline

Follows [T-001](./T-001.md), which is locked and unresolved. T-002 does not attempt
to resolve T-001. It measures a narrower thing the current single-arm design can
actually observe.

## Required limitation language

> Phase one measures responsiveness to items Tacit successfully routed. It does not
> observe all time-sensitive items the relevance filter missed, so it establishes a
> workflow baseline rather than evidence that routing is the primary cause of missed
> opportunities.

Also:

- This is observational.
- This is single-user.
- This is not causal.
- Notification-to-view latency is conditioned on owner availability.
- First-view-to-decision latency is the cleanest context-related signal.
- Total system latency includes polling cadence, processing delay, notification
  delay, availability, and decision time.
- False-negative visibility begins only after rejection logging is deployed.
- Historical missed items cannot be reconstructed unless a rejection log already
  existed — it did not.
- The rejection audit is separate from the primary enrolled population.
- A rejected item later marked `time_sensitive` must never enter or alter the
  primary population.

## T-002A — Instrumentation reliability

**Claim:** Tacit can capture a sufficiently complete and auditable lifecycle record
for the prospectively enrolled proposal population.

**Confidence:** 90%

T-002A succeeds only if all of the following hold, evaluated at the end of the
observation horizon:

- At least 80% of enrolled proposals have non-null `notification_accepted_at`
- At least 60% have non-null `first_viewed_at`
- At least 95% have non-null `proposal_created_at`
- At least 95% have a valid normalized `outcome` by the end of the observation
  horizon
- No duplicate Gmail message ID is enrolled twice
- No rejected message enters the primary population
- No lifecycle timestamp is fabricated from another timestamp
- Every latency metric shows its denominator

**Instrumentation canary:** any proposal with non-null `decision_at` and null
`first_viewed_at` is an instrumentation inconsistency.

```
decided_without_view_count / decided_item_count
```

T-002A fails if this rate exceeds 5%. If it exceeds 5%, never-viewed counts are
considered unreliable and cannot support T-002B. Computed live in
`lib/t002.ts:computeInstrumentationCanary` and shown on `/experiments/t002`.

`computeInstrumentationCanary` returns an explicit `state` — `"no_data"`,
`"within_threshold"`, or `"breached"` — rather than leaving the UI to infer pass/
fail from the rate. This matters specifically for the zero-decisions case: with
`decidedItemCount === 0`, `rate` is `null` (never 0), and `state` is `"no_data"`,
which the dashboard renders as "No decisions yet" — distinct from
`"within_threshold"`. Before this fix, the dashboard inferred pass/fail from
`rate > 0.05` in the UI component itself, which meant a null rate (no decisions
at all — the actual state of the live population as of this writing) evaluated
`breached` to `false` and rendered as "within threshold," misrepresenting "not
yet evaluated" as "checked and passed." See "Known integrity limitation" below
for the rest of the concurrency fixes made alongside this.

## T-002B — Diagnostic usefulness

**Claim:** The measured workflow stages reveal at least one pre-registered,
non-trivial diagnostic pattern.

**Confidence:** 55%

Succeeds only if at least one of these three signals occurs:

**Signal 1 — unresolved after view.** At least 25% of viewed proposals remain
unresolved 24 hours after `first_viewed_at`, with at least 10 eligible viewed
proposals.

Precisely defined and computed in `lib/t002.ts:computeSignal1`:

- **Eligible denominator:** enrolled proposals with non-null `first_viewed_at`
  where at least 24 hours have elapsed since that view.
- **Numerator:** among the eligible denominator, proposals with no decision
  inside the first 24 hours after `first_viewed_at` — covering (a) still
  unresolved, (b) eventually decided but more than 24h after viewing, and
  (c) expired after view without a decision inside the first 24h (expiration
  never sets `decision_at`, so these fall out of the "no decision" case with no
  special-casing).
- **Excluded from the denominator entirely:** missing `first_viewed_at`, fewer
  than 24h elapsed since view, and any negative interval (a `first_viewed_at` in
  the future relative to "now," or a `decision_at` preceding `first_viewed_at` —
  both indicate untrustworthy timestamp data).
- **Threshold:** `signal1MinimumReached` requires `signal1EligibleCount >= 10`;
  `signal1ThresholdMet` additionally requires `signal1Rate >= 0.25`.

Shown on the dashboard's "Signal 1" section as `signal1EligibleCount`,
`signal1UnresolvedAt24hCount` / `signal1EligibleCount` (numerator/denominator),
and `signal1Rate`.

*(Earlier draft of this instrumentation used "Viewed, unresolved" — a
point-in-time snapshot of currently-pending-and-viewed proposals with no 24-hour
gate — as a stand-in for this signal. That metric answers a different, real
question ["how many pending items are sitting unresolved right now"] but does
not implement Signal 1's time-gated definition and cannot be used to resolve it.
It is retained on the dashboard as `viewedButUnresolvedCount` under "Coverage,"
relabeled to make clear it is not Signal 1.)*

**Signal 2 — classification difference.** Compare `actionable` vs `needs_caleb`:
succeeds only if both groups have ≥5 resolved proposals, the median
`first_viewed_at → decision_at` differs by ≥2×, and the absolute median difference
is ≥4 hours. **Marked likely unreachable above** given the historical data gap. Not
surfaced on the live dashboard (the required page-field list doesn't include it);
computed via ad hoc SQL at resolution time instead:

```sql
SELECT classification,
       count(*) FILTER (WHERE decision_at IS NOT NULL) AS resolved_n,
       percentile_cont(0.5) WITHIN GROUP (
         ORDER BY extract(epoch FROM (decision_at - first_viewed_at))
       ) AS median_seconds
FROM pending_proposals p
JOIN t002_observations o ON o.proposal_id = p.id
WHERE classification IN ('actionable', 'needs_caleb')
  AND decision_at IS NOT NULL
  AND first_viewed_at IS NOT NULL
  AND decision_at - first_viewed_at >= interval '0'
GROUP BY classification;
```

(`decision_at - first_viewed_at >= interval '0'` excludes negative intervals —
consistent with how `medianIntervalMs` treats them everywhere else in this
codebase; a single clock-skewed row would otherwise silently skew the median used
to resolve this signal. The `classification IN (...)` filter is explicit rather
than relying solely on the fact that no other value is inserted today —
`pending_proposals.classification` has no DB-level CHECK constraint.)

**Signal 3 — filter misses.** At least 2 manually reviewed `filter_rejections` rows
are marked `time_sensitive`, out of at least 20 reviewed. Numerator and denominator
both shown on the dashboard ("Time-sensitive" / "Reviewed").

If none of the three signals occurs, T-002B fails.

## Primary population

The first 15 eligible Gmail proposals created after deployment. Enrolled
prospectively and immutably via `t002_observations` (keyed uniquely to
`proposal_id`, populated only by the atomic `t002_try_enroll()` function — see
`supabase/migrations-09-t002-instrumentation.sql`).

Excluded from the primary population:

- Duplicate Gmail message IDs — enforced structurally: `pending_proposals` has a
  unique constraint on `gmail_message_id`, so a duplicate never even becomes a
  proposal row, let alone an enrollment.
- `ignore`-classified messages (Tacit's existing spam/automated-no-reply
  classification, produced by `handle_email` before a proposal is ever created —
  see limitation below).
- Rejected messages later discovered through the `filter_rejections` audit review —
  structurally separate table, never promoted into `pending_proposals`.
- "Internal tests explicitly marked as tests" — **no mechanism to mark a message as
  an internal test currently exists in this codebase.** This exclusion is a
  documented no-op until such a mechanism is built; it does not silently fail
  because nothing currently produces a message that would need excluding this way.

Requirements enforced by `supabase/migrations-09-t002-instrumentation.sql`:

- One proposal enrolls at most once — `t002_observations.proposal_id` is a primary
  key referencing `pending_proposals(id)`.
- No more than 15 can enroll, and concurrency cannot exceed the cap — enforced by
  `t002_try_enroll()`, which increments a singleton counter row inside a
  WHERE-guarded UPDATE (Postgres's row lock on that single row serializes every
  concurrent caller against the same cap check) before inserting into
  `t002_observations`.
- Enrollment occurs only after deployment — enrollment is only ever attempted from
  `lib/inbox-watch.ts` at the moment a new proposal row is inserted; no backfill
  enrolls any pre-existing row (the one proposal created 2026-07-29, before this
  code existed, is not and will never be enrolled).
- Rejected items cannot enroll later, and outcome changes do not affect enrollment
  membership — `t002_observations` is written once at enrollment and never updated;
  all downstream state (`status`, `outcome`, timestamps) lives on
  `pending_proposals` and is irrelevant to whether a row is a member.

## Lifecycle timestamps

`source_received_at`, `detected_at`, `filtered_at`, `proposal_created_at`,
`notification_attempted_at`, `notification_accepted_at`, `first_viewed_at`,
`decision_at`, `sent_at`, `skipped_at`, plus `expired_at` for the terminal timeout
state. `created_at` behavior is unchanged.

**Known limitation — `detected_at` and `filtered_at` share one real timestamp.**
Tacit's pipeline filters an entire fetched batch in one pass
(`relevanceFilter(messages)` in `lib/inbox-watch.ts`). For a kept message there is no
earlier real "detected" instant distinct from "passed the filter" — both are set to
the same real capture taken once per watch run, immediately before filtering. This
is disclosed rather than smoothed over; it is not a fabricated timestamp (a
fabricated timestamp would be inventing a plausible-but-fake *earlier* moment — this
is one real moment used honestly for two simultaneous events).

`notification_accepted_at` is set only when Resend's API response is actually
inspected and contains a message id with no error (`lib/t002.ts:interpretResendResult`,
wired through `lib/email.ts:sendMessageToOwner`). **This confirms Resend accepted the
send request — never that the email was delivered to or opened by the owner.** No
delivery webhook exists in this codebase. This value must never be described as
"delivery" anywhere in code, UI, or future analysis.

**`source_received_at` can silently be a processing-time substitute, not a
genuine receipt time.** `GmailChannel.fetchNew()` (`lib/relevance/channels/gmail.ts`)
falls back to `new Date().toISOString()` when the Gmail `Date` header is missing.
A new `source_received_at_inferred` boolean column (set explicitly at insert time
in `lib/inbox-watch.ts`, `NULL` for pre-existing/backfilled rows where it's
unknown either way) records when this happened. `lib/t002.ts:totalSystemLatencyPairs`
excludes rows where this flag is `true` from the "Total system latency" median —
the other two medians (notification→view, view→decision) don't depend on
`source_received_at` and are unaffected. This exclusion is silent in the sense
that it just shrinks that one median's `n`; it is not separately surfaced as its
own count on the dashboard.

## Normalized outcome values

`pending`, `sent`, `skipped`, `expired`, `failed` — stored in the new
`pending_proposals.outcome` column (CHECK-constrained). The pre-existing `status`
column (`pending`/`sent`/`skipped`, now widened to also admit `expired`/`failed`) is
kept and still drives the `/inbox` page's own queries — `outcome` is additive, not a
replacement.

`failed` is defined in the schema per spec but is not currently produced by any code
path (no proposal-level failure state exists yet — a failed *notification* still
leaves the proposal `pending` for manual review via "Check inbox"). Reserved for a
future failure mode, not fabricated to have occurred.

## Expiration

Server-side, deterministic, idempotent, via the `t002_expire_overdue(p_hours)`
Postgres function: expires only enrolled (`t002_observations`-linked), still-`pending`
proposals whose `enrolled_at + T002_OBSERVATION_HOURS` has passed; guarded by
`WHERE status = 'pending'` (never overwrites `sent`/`skipped`) and
`WHERE expired_at IS NULL` (records expiration exactly once). Invoked from
`GET /api/owner/inbox`, `GET /api/owner/experiments/t002`, and once per
`runInboxWatch()` run — no client timers anywhere.

`T002_OBSERVATION_HOURS` — environment variable, default **168** (7 days) when unset.

## Known integrity limitation — Gmail send is not atomic with the database

An adversarial review of the first implementation found that the guarded
send/skip status transition (`WHERE status = 'pending'`) could affect zero rows
— because expiration claimed the row first, or a duplicate/racing PATCH already
transitioned it — while the route still returned `{ok: true}` unconditionally.
Since the real Gmail send (`app/api/owner/email/send/route.ts`) happens
**before** the follow-up `PATCH /api/owner/inbox/[id]` call that records
`decision_at`/`outcome`/`sent_at`, a lost race meant: the email was genuinely
sent, but the database silently kept whatever state won the race (e.g.
`expired`), with no error surfaced anywhere and no way to reconcile after the
fact.

**What was fixed:** `PATCH /api/owner/inbox/[id]` now returns HTTP 409 with
`{"error": "Proposal is no longer pending", "code": "PROPOSAL_NOT_PENDING"}`
when the guarded update affects zero rows (`lib/t002.ts:classifyGuardedTransition`).
No decision timestamp, outcome, or event is written in that case — the guard
itself already prevented that; the fix is that the caller is now told. The
client (`app/inbox/view.tsx:markStatus`) checks `res.ok`, never removes the
proposal from its local list on failure, surfaces a visible error banner, and
reloads the inbox from the server on a 409 so the UI reflects authoritative
state rather than a stale optimistic guess. The same fix applies to
`POST /api/owner/inbox/[id]/view` (see "First-view tracking" below), which now
also guards on `status = 'pending'`.

**What this does *not* fix, and is not claimed to fix:** the Gmail send and the
database write are still two separate operations with no shared transaction —
there is no distributed transaction here, and this patch does not create one.
If expiration (or a race) wins after a real Gmail send has already completed,
the owner now gets a **visible** 409 instead of silence, and can notice and
manually reconcile — but the `pending_proposals`/`t002_observations` data for
that row will still record something other than "sent" (e.g. `expired`) even
though the email genuinely went out. `app/api/owner/email/send/route.ts` has a
block comment marking this explicitly.

**Why no reservation state was added:** the task considered a
`pending -> sending -> sent` reservation (claim the row *before* calling Gmail,
so expiration/duplicate-PATCH can never claim a row mid-send) but this route
currently has no `pending_proposals` id at all — only envelope data
(recipient/subject/body). Implementing the reservation would require adding a
new `sending` status value, threading a proposal id through
`components/EmailProposalCard.tsx` and this route, and adding new UI states —
a broader schema/UI change than this fix pass is scoped to. Per explicit
instruction, this was not improvised; the false-success bug is fixed now (no
more silent 200 on a lost race), and this section documents the remaining gap
plainly rather than glossing over it.

## First-view tracking

Owner-authenticated (`requireOwner()`), server-timestamped, atomic, and idempotent:
`POST /api/owner/inbox/[id]/view` runs
`UPDATE pending_proposals SET first_viewed_at = now() WHERE id = $1 AND status = 'pending' AND first_viewed_at IS NULL`.
Postgres's row lock means at most one concurrent caller's UPDATE can affect the row,
so a "viewed" `proposal_events` row is logged at most once per proposal. Triggered
by `app/inbox/view.tsx` when a proposal row is expanded (not on collapse).

The `status = 'pending'` guard (added alongside the integrity fix above) means a
stale client — e.g. a browser tab holding an old fetch of the pending list, from
before a proposal expired or was sent/skipped elsewhere — can never write
`first_viewed_at` or log a `viewed` event for a proposal that has since left the
`pending` state. When the guarded update affects zero rows,
`lib/t002.ts:classifyFirstView` uses a read-only follow-up lookup (not itself a
write, so it cannot race the update) to distinguish three cases in the response:
not found (404), no longer pending (`200 {viewed:false, code:"PROPOSAL_NOT_PENDING"}`),
or already viewed (`200 {viewed:false, code:"ALREADY_VIEWED"}` — the common,
idempotent no-op on every re-expand).

## Proposal event log

Append-only `proposal_events` table. Allowed `event_type` values: `detected`,
`passed_filter`, `proposal_created`, `notification_attempted`,
`notification_accepted`, `viewed`, `sent`, `skipped`, `expired`, `failed`. Columns:
`id`, `proposal_id`, `event_type`, `occurred_at`, `metadata` (jsonb), `created_at`.

`metadata` is sanitized through `lib/t002.ts:sanitizeEventMetadata`, which strips any
key matching a forbidden list (`body`, `draft`, `draft_body`, `email_body`, `token`,
`access_token`, `refresh_token`, `secret`, `snippet`, `content`, `attachment`) and
drops any string value over 200 characters — defense in depth on top of the fact that
no current call site passes anything beyond an empty object. No event row ever
contains a full email body, draft, OAuth token, secret, or document content.

Idempotency: the `viewed` event is only inserted when the guarded first-view UPDATE
actually affects a row (see above). The `sent`/`skipped` events are only inserted
when the guarded `WHERE status = 'pending'` PATCH actually affects a row, so a
proposal can't be double-transitioned into logging two terminal events.

## False-negative audit (`filter_rejections`)

**Rejected messages were not previously persisted anywhere** — confirmed by
inspection: `lib/relevance/filter.ts` only `console.log`s coarse/smart drops. This is
new, forward-only infrastructure.

Table: `id`, `gmail_message_id` (unique — a still-unread message re-dropped on a
later run doesn't duplicate), `source_domain`, `source_identifier` (normalized
sender address only), `rejected_at`, `review_outcome`
(`unreviewed`/`time_sensitive`/`not_time_sensitive`, default `unreviewed`),
`reviewed_at`, `created_at`. **No subject, snippet, or body is stored** — domain and
sender identifier are sufficient for a human to manually cross-check against Gmail.

Review mechanism: documented SQL (see comments in
`supabase/migrations-09-t002-instrumentation.sql`), not a new endpoint or dashboard —
smallest production-safe mechanism, per spec.

```sql
-- List unreviewed rejections:
SELECT id, source_domain, source_identifier, rejected_at
FROM filter_rejections
WHERE review_outcome = 'unreviewed'
ORDER BY rejected_at DESC
LIMIT 50;

-- Mark one reviewed:
UPDATE filter_rejections
SET review_outcome = 'time_sensitive', reviewed_at = NOW()  -- or 'not_time_sensitive'
WHERE id = '<uuid>' AND review_outcome = 'unreviewed';
```

A reviewed rejection remains outside the primary population forever — there is no
code path anywhere that promotes a `filter_rejections` row into `pending_proposals`.

## Source-history signals (explicitly not a trust mechanism)

Passive signals derivable from proposal history (normalized sender identifier,
source domain, prior sent count, prior skipped count) are not implemented in this
pass, and if implemented later must never feed approval, sending, ranking,
prioritization, or automation — the human-approval step in
`components/EmailProposalCard.tsx` / `app/api/owner/email/send/route.ts` is
untouched by this work and stays untouched.
